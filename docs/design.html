golden flow。

A question becomes tickets, tickets gather their evidence, options and code, and the work is finished when a live number says so. Every page in between keeps itself current.

design for review · not built 2026-10-21 refs: Mobbin (Linear, Jira, Plane, Amplitude, Miro…) extends docs/washi.html §04 work

30-second version

  • Investigation is a page type. Question, live evidence, hypotheses with states, findings. A finding turns into a ticket in place and then shows that ticket's status.
  • Tickets are Linear-quiet, Jira-complete. A calm centre column and a right rail of cards: Properties · Watching · Development · Canvas. They open as a peek over the board or as a full tab.
  • Metrics are first-class. A named number with a target. Tickets watch it, stat pages chart it with deploy markers, and a Done when item ticks itself.
  • Integrations are cards, never copies. A GitHub app attaches PRs by key, shows checks, reviews and deploys, and moves the ticket by rule. Washi never reviews the code.
  • Done has a second half. A deploy moves the ticket to Done and starts a 7-day verifying watch. A miss makes a linked follow-up and leaves the original ticket closed.
00 · called

The six open questions, decided

I decided each one so this design can be judged as a whole. Each choice has a reason, and any of them can be overruled.

QuestionCallWhy
Metric: own object or an expr? own object a metrics table in the workspace file, defined over a table (ink) or a fetched source (tsuru) Watches, targets and deploy markers need a stable id. A page shows a metric through <Metric> and <MetricChart>, so pages are still inert WSX.
Ticket keys per project WEB-142, API-31 That's how Linear and Jira do it, and keys stay short. The team-space starter makes one project named after the workspace.
Done = merged or deployed? deployed or merged when no deploy feed exists, plus a verifying badge while a watch runs "Shipped" means users have it. Verifying is a badge, not a column, so the board stays four columns.
How integrations connect GitHub App + webhooks per workspace (hosted); the desktop polls Events arrive in seconds. Connecting the app is the approval for these reads. Outward writes (Slack posts, Sentry reopen) still stop at the desk.
Linear / Jira one-time import, no two-way sync A sync locks Washi to their data model. An import lets a team move in, and a later sync can be added if teams ask for it.
Metric misses its target follow-up ticket linked follow-up of; the finding reopens Reopening would rewrite sprint history. A follow-up keeps the record honest and puts the work back in the investigation, where the question lives.

screen 5 · the full ticket

  1. Header in three facts: status, the watched metric against its target, and where the ticket came from. These are what someone opening a ticket wants to know first.
  2. Approach comes from the canvas. Choosing a node writes this block and lists the rejected options, so the reasoning travels with the ticket.
  3. Done when can be bound. A bound item shows bound · ticks itself and can't be ticked by hand. It ticks when the metric holds its target for the whole window.
  4. One Activity stream for comments, moves, PR events and Washi's actions, with filters. The composer takes comments and asks: "@Washi summarise this thread" answers inline, marked as Washi's.
  5. The rail is a stack of cards (Jira's grouping, Linear's calm). Properties are always there; Watching, Development and Canvas show only when they exist.
  6. Development is read-only. PR state, checks as a bar of cells, review, diff size and deploys. Clicking opens GitHub. Washi reads it and doesn't comment on it.

screen 7 · Verify flow — options, after the vote

  1. The ribbon names the ticket the canvas serves, with its live status. A canvas made from a ticket starts seeded by Washi: the problem in the centre and the findings around it.
  2. Chosen is a state, not a colour someone picked. It writes the ticket's Approach block. Rejected options grey out but stay, with their chips as the reasons. Any node can be turned into its own ticket.
  3. Votes are a timed session with one vote each, then results. They inform the decision; a person still makes it with Choose.

Toolbar extras beyond the basic shapes: ∿ drops a live metric chip on a node, ⌕ links evidence, and 和 asks Washi to lay out or cluster the options people wrote. Washi never adds options of its own unless asked.

10 · system

What it takes

Mostly new chrome on existing pieces. There are five new records (metrics, watches, links, integration events, rules) and four new WSX primitives. The C1 rule holds: everything lives in the workspace file.

PieceStatusShape
Ticketshaverows of issues + row pages. Add: key (project prefix + seq), the ticket frame in studio
Ticket framenewstudio chrome around a row page: header chips, rail cards, Relations, Activity (outside the sheet, like page chrome, Q18)
Peekhaverow drawer exists; restyle to screen 4, add ↑↓ to walk the column
Typed linksnewlinks(from, to, kind); kinds: from · blocks · related · follow-up · explores · implements · watches. Backlinks read the same table
Metricsnewmetrics(id, name, def, unit, grain); def = ink aggregate or tsuru source; history via record_changes/snapshots
Watchesnewwatches(ticket, metric, op, target, days, started_at, state); the routine clock checks daily
Integration eventsnewintegration_events(source, ref, kind, payload, at) from webhooks; cards are a projection; Activity reads them
Rulesnewper-project event → status map; moves logged by rule
WSXnew<Metric> · <MetricChart target markers> · <Finding ticket> · <Hypothesis state>
Canvas votes + Chosennew<Node state="chosen|out">; votes are ephemeral (runtime memory) until ended, then written as node props
Washi toolsnewticket_from_finding, link_add, metric_read; all page/table writes, no new approval class
Invariants this design keeps
  • C1: metrics, links, watches and events are rows in the workspace SQLite file. Postgres stays identity-only.
  • WSX stays inert: a metric is referenced by id; its definition is data, evaluated by the repository, never by the page.
  • Q18: the ticket frame is studio chrome; the body is still a sheet authored by the sheet.
  • The desk: integration reads are approved by connecting; anything outward (Slack post, Sentry write) asks.
  • History: rule moves go through updateRecords, so charts replay them.
11 · build

Build order, one PR each

Ordered so each step ships something usable. Tickets and links come first because every later screen hangs off them.

  1. Keys + ticket frame — WEB-142, /t/WEB-142, header chips, Properties card, keyboard.
  2. Typed links + Relations — the links table, Relations section, backlinks on every page.
  3. Activity — one stream from record changes, comments and Washi actions, with filters and an inline ask.
  4. Board v2 + peek — signal row, verifying-aware progress, filters, the new peek.
  5. Investigation template — Hypothesis, Finding, Make ticket (single + batch).
  6. Metrics — definitions, <Metric>, <MetricChart> with target, stat page focus mode.
  7. Watches + bound Done-when — the daily check, verifying badge, the follow-up on a miss.
  8. GitHub integration — app, webhooks, events, Development card, deploy markers on charts.
  9. Rules — the per-project event → status map.
  10. Canvas: Chosen + votes — states, vote session, Approach write-back, node → ticket.
  11. Resolution + review — Washi's resolution draft, Inbox rows, the review routine line.
  12. Linear / Jira import — one-time, keys preserved as an alias.
12 · judge it

What to look at before saying go

These are the five calls most likely to be wrong. A yes or no on each is enough to start step 1.

  1. Rail of cards vs Linear's single property list. Cards make room for Watching and Development, but cost density. Screen 5.
  2. Verifying as a badge on Done rather than its own column. Screen 3.
  3. Done-when bound to a metric can't be ticked by hand. This is strict on purpose; is it too strict? Screen 5, note 3.
  4. Votes inform and a person chooses. Should Choose top exist at all? Screen 7.
  5. Metrics as their own object instead of an expr on a page. It adds a concept and buys watches. §10.
